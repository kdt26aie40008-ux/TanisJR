### 実機で分かったこと
- Ollama 0.40 は **LoRA アダプター単体の読み込み**にも、**GGUF の登録時量子化**にも対応していない。統合済みモデルを safetensors のまま `ollama create -q q4_K_M` で取り込む方式にした。
- 学習率 2e-4・3エポックでは少量データで出力が崩れた（「相棒、相棒、相棒」）。既定を 1e-4・2エポックに下げた。
- 30件の人工データでは、1.7B モデルの返答は話し方の一部が変わる程度で、qwen3:8b より明らかに品質が低い。実用には良質なデータを増やすか 8B での学習が必要。

### 修正: AI が自分の名前を第三者だと思う（2026-11-08）🟡
- 症状: 設定で AI の名前を「はやと」にしても、「はやと、今日何してた？」に「はやとって人に聞いて」のように、名前を別の人として扱って返す。
- 原因: 人格プロンプトには「あなたの名前は『○○』です」と書いてあるだけで、「○○と呼ばれたら自分への呼びかけ」とは伝えていなかった。設定の「AI の名前の読み」（`wake_reading`）もプロンプトに入っていなかったので、漢字やローマ字の名前を読みで呼ぶと知らない名前になっていた。記憶の抽出も AI の名前を知らないので、呼びかけた名前をユーザーの知り合いとして記憶するおそれがあった。
- 対応（`services/persona.py`）: 冒頭に「○○（読み）はあなた自身の名前で、別の人ではない。『ねえ、○○』『○○くん』などはあなたへの呼びかけで、続く質問はあなたへの質問。『○○に聞いて』のように第三者として扱わない」を追加。最後の念押しにも1行追加。関連する記憶があるときは「記憶に○○が出てきたらあなたのこと」と添える。会話・自分から話しかける・学習の教師プロンプトで読みも渡す。
- 記憶の抽出（`services/extraction.py`）に AI の名前と読みを渡し、その名前を別の人として記憶しない・呼びかけ自体は抽出しないよう指示。
- テスト: backend 250件（回帰テスト: 名前を第三者扱いしない指示・読みの扱い・抽出側への名前の受け渡し）、frontend 107件。
- 実機の qwen3:8b に、プロンプトだけを直接渡して確認（アプリのサーバーは使わず、プロフィール・記憶は空）: 「はやと、今日何してた？」など3通り×3回。修正後は9回とも自分のこととして答えた。ただし修正前のプロンプトでも、この条件では第三者扱いは再現しなかった（報告された症状は、実データのプロフィールや記憶が関係している可能性がある）。
- 残る問題: 「今日何してた？」に「映画を見てた」などの体験を作って答えることが修正前後とも多い（「体験を作り話にしない」を加えたが、8B では守られないことがある）。1回「お前は？」と言った。
- 未確認: 実際のアプリ（実データのプロフィール・記憶あり）での返事。すでに保存されている、名前を別の人として扱った記憶は自動では直さない（思い出画面で削除・修正が必要）。

### 修正: 数式の読み上げ・積分の表示・相づち（2026-11-06）
- 読み上げ: `x^22` を「xの2乗 2」と読んでいたのを「xの22じょう」に。`x^{-1}` は「マイナス1じょう」。「乗」は「のり」と読まれないよう、ひらがなで渡す。積分・総和の上下の数を累乗と読んでいたのを「0から1までの積分」「k=1からnまでの和」に、`dx` は「ディーx」に。数式の外に書かれた `x²` `2^22` `10⁻³` や ∫ √ π × ÷ ≤ ≥ ≠ も読む。
- 表示: 文中の数式に積分・総和・分数・極限があると、文の高さに押し込まれて小さく潰れていたため、その数式だけ別行の数式と同じ大きさで描き、積分の `dx` の前に少し間をあける。ふつうの文中の数式（`x^2` など）は今までどおりの大きさ。
- 相づち: 内容に関係なくランダムだったのを、聞き取った言葉に合わせて選ぶ（つらい話 →「そっか…。」、うれしい話 →「いいね。」、頼みごと →「うん、わかった。」、質問 →「えっとね、」、あいさつ・短すぎる言葉には入れない）。相づちは聞き取りが終わってから入れる（GPU で 0.3秒程度）。
- 実機: 積分の表示はブラウザで変更前と後を見比べて確認。読み上げは AivisSpeech で実際に聞いての確認はまだ（文字への変換は単体テストで確認）。

### 修正: 名前を呼んでも反応しない（2026-11-06）
- 原因: 音声認識の設定が GPU（cuda）だが、この PC には GPU 用ライブラリ（cublas64_12.dll）がない。毎回 GPU で読み込み → 失敗 → CPU で読み込み直し、をしていたため1回10秒以上かかり、呼びかけの聞き取りが順番待ちで詰まっていた。
- GPU が使えないと分かったら、その起動中は CPU を使い続ける（知らせるのは最初の1回だけ）。
- 呼びかけの照合で、漢字1文字の名前（「漆」など）も使う（読み「うるし」が漢字で書き起こされることがあるため）。
- 音声認識を GPU で動かすライブラリ（nvidia-cublas-cu12 / nvidia-cudnn-cu12、約1GB）を `backend/requirements-gpu.txt` に分け、`start.ps1` が NVIDIA の GPU を見つけたときだけ自動で入れる。アプリは仮想環境内のライブラリを読み込む。入っていなければ CPU で動く。
- 量子化・蒸留も検討したが、CPU ではすでに int8 量子化済みで、公開されている日本語の蒸留版（kotoba-whisper）も重い「音を聞く部分（エンコーダー）」は同じ大きさのため、速さはほぼ変わらない。GPU 化を選んだ。
- 呼びかけの聞き取りでは、AI の名前と読みを聞き取りのヒント（hotwords）として渡す。ほかの聞き取り中は、呼びかけの聞き取りを待たずに飛ばす（マイクのボタンで話した声が後回しにされ、返事が来なかった原因）。呼びかけを待ち始めたときにも音声認識を準備する（GPU の初回は約20秒）。
- 実機（合成音声、GPU）: 1回 0.3〜0.5秒（CPU では 9〜25秒）。「ねえ、うるし」「うるし」「ねえうるし、明日の予定は？」「うるしちゃん」「おーい、うるし」すべて「うるし」と聞き取れた（ヒントなしでは「ブルシ」「うれしい」になっていた）。「今日はいい天気だね」「それは嬉しいな」「ねえ、ちょっと聞いて」は名前に変わらない。GPU 使用量は会話モデルと合わせて約7.5GB / 8GB。
- 未確認: 実際のマイクで話しかけたときの動作（合成音声を直接送って確認）。

### 改善: 予定を会話で確かめて決める（2026-11-06）
- 「〜の予定を入れて」と言うと、AI が内容を復唱し、通知の時間が決まっていなければ「通知は何分前がいい？」と聞く（依頼に通知の時間が入っていれば聞かずに「これで進めていい？」）。次の返事が了承（「うん」「30分前で」「通知はいらない」）なら実行、断り（「やっぱやめとく」）なら破棄、直す指示（「やっぱ16時にして」）なら確認中の下書きだけを直してもう一度確かめる。変更・削除も同じ流れ。チャットのカードのボタンでも決められる（どちらで決めても二重に実行しない）。
- はっきりしない返事・関係ない話では実行しない（最後にもう一度確認する）。確認待ちは10分で会話からは外れる（カードのボタンでは引き続き決められる）。

### 修正: 数式が記号のまま表示される（2026-11-06）
